# مقترح مراجعة المالك: هوية UCP وWeb Bot Auth

14 أكتوبر 2026 — **مقترح فقط؛ لا نشر، لا مفاتيح حقيقية، لا نطاق مختار، ولا طلب إلى متجر.**

## القرار المطلوب لاحقًا

لا يُطلب اعتماد نشر الآن. قبل التنفيذ سيُعرض على المالك عنوان الاستضافة الفعلي، والملف النهائي كاملًا، ومفتاح التحقق العام الفعلي، وتكلفة وشروط الاستضافة، وصلاحياتها، وخطة التراجع. موافقة المالك التقنية ليست ترخيصًا لاستخدام أسعار ألف تجاريًا. تكامل ألف معلّق حتى تحقق شرطَي الهوية المناسبة وحق الاستخدام بشكل مستقل.

## ما الذي تقترح إتاحته للعامة؟

| العنصر | المحتوى الدقيق المقترح | الغرض | ما ينكشف/المخاطر | الإلغاء أو التغيير |
|---|---|---|---|---|
| ملف HTTPS لهوية الوكيل، مسار مقترح `/.well-known/ucp` على مضيف لم يُحدد | إصدار UCP `2026-08-25`، نقل MCP، قدرات البحث والاستعلام عن الكتالوج فقط، `payment_handlers` فارغ، ومفتاح تحقق عام بعد موافقة منفصلة | تعريف قدرات الوكيل والتحقق من مصدر طلباته | ربط مضيف WIFQA بالوكيل؛ الملف قابل للنسخ والتخزين المؤقت؛ لا يمكن ضمان سحب النسخ السابقة | تعطيل الطلبات أولًا؛ سحب الملف أو إرجاع 410 بعد موافقة مناسبة؛ تحديث مسار profile في العميل عند تغيير المضيف؛ انتظار انتهاء التخزين المؤقت |
| JWK عام داخل `keys` في الملف نفسه | نوع المفتاح وخوارزميته ومعرفه ومكوناته العامة فقط، بلا `d` أو أسرار | التحقق من توقيع HTTP؛ ليس كلمة مرور ولا إذنًا لشراء أو استخدام البيانات تجاريًا | إذا سُرق المفتاح الخاص، يمكن انتحال الوكيل ما دام العام مقبولًا لدى المتحقق | وقف التوقيع بالمفتاح القديم فورًا؛ نشر مفتاح بديل بعد الموافقة؛ إزالة القديم من كل ملفات/مرايا المفاتيح؛ الإبطال قد يتأخر لدى جهات خزّنته مؤقتًا |
| بيانات الطلب عند تجربة لاحقة مصرح بها | URL للـprofile ومعرف المفتاح وتوقيع قصير الصلاحية ووقت وnonce وبصمة جسم الطلب؛ بحث AirPods 4 فقط | التعريف ومنع إعادة التشغيل وربط التوقيع بالحمولة | المصدر يرى هوية الوكيل وعنوان IP للخادم وعبارة البحث والتوقيت؛ قد يسجلها | وقف الموصل فورًا؛ تعطيل إعداد provider؛ لا يمكن محو سجلات المصدر بمجرد الوقف |
| المضيف العام نفسه | لم يُحدد؛ `wifqa.invalid` في النماذج مثال غير قابل للاستخدام فقط | عنوان قابل للوصول للملف | قد تكشف DNS/TLS اسم المضيف؛ الاستضافة قد تنشئ شروطًا أو كلفة | لا تسجيل ولا ربط قبل تحديد الشروط وموافقة المالك؛ التغيير يحتاج تحديث URL وعدم ترك نطاق متروك لانتحال الهوية |

لن يُنشر في هذه الخطة: مفتاح خاص أو API token، بيانات المالك أو العملاء، بريد شخصي، بيانات Drive، ملفات المستودع الخاص، webhooks أو checkout أو دفع أو قدرات شراء. اسم WIFQA في عنوان الوثيقة فقط؛ لا حاجة إلى إضافة حقل هوية تجاري غير محدد في مخطط UCP.

## النماذج المرفقة

- `ucp-proposal/agent-profile.review-only.json`: نسخة قراءة كتالوج مشتقة من بنية المثال الرسمي مع حذف الشراء والطلبات والدفع. `keys` فارغ عمدًا؛ صالح نحويًا كـJSON لكنه **غير جاهز للمصادقة أو النشر**.
- `ucp-proposal/public-key.placeholder.json`: يبين فقط حقول المفتاح العام المحتملة. قيم `x` و`y` ومعرف المفتاح placeholders وليست مادة تشفير أو JWK صالحًا. لا أُنتج مفتاحًا حقيقيًا.
- `ucp-proposal/tools-list.review-only.json`: حمولة اكتشاف نموذجية، ليست طلبًا مرسلًا. يستخدم مضيف `.invalid`، ولا يستخدم ملف Shopify التجريبي لانتحال هوية وكيل آخر.

## الحاجة المؤكدة وما لم يُختبر

المؤكد وثائقيًا: Storefront Catalog MCP في Shopify يطلب profile URL في `meta.ucp-agent.profile` لكل طلب؛ المثال الرسمي يدعم إصدار `2026-08-25` وقدرات catalog. ملف العام لا يمنح حق إعادة توزيع بيانات المتجر. تقرير المصدر الحالي نقل اشتراط ألف Web Bot Auth لحركة الخادم.

غير المؤكد عمليًا: لم يُرسل `tools/list` أو أي طلب موقّع لألف؛ لم يُختبر قبول هذه البنية المختصرة أو خوارزمية محددة أو ترتيب الـheaders أو endpoint الصحيح أو المعدلات أو نتيجة بحث. Shopify يصف مستوى Anonymous بلا توقيع، لكنه لا يلغي اشتراط المتجر الخاص ولا يسمح بتجاوزه. لا نستنتج أن كل البدائل تحتاج توقيعًا أو نطاقًا جديدًا.

ملاحظة توافق: لا نخلط إصدار UCP الأحدث المتغير مع إصدار متجر ألف `2026-08-25`. مثال Shopify لهذا الإصدار بلا مفاتيح، بينما مواصفات UCP للإصدار نفسه توثق `keys`. يجب اختبار المخطط الإصدارِي والخوارزمية المقبولة محليًا أولًا. Shopify يذكر ECDSA P-256 للمستوى Signed؛ لا يكفي ذلك وحده لإثبات قبول مسار Web Bot Auth لدى ألف. إذا ظهرت ضرورة حقول إضافية، تُعرض الإضافة على المالك قبل نشرها.

## مراحل التنفيذ المقترحة والبوابات

1. الآن: تجهيز ومراجعة هذه الملفات داخل فرع خاص فقط؛ فحص JSON، مراجعة حد المعلومات المنشورة. بلا أسرار أو اتصالات متجر.
2. قبل أي نشر: تحديد مضيف موجود مصرح به وتأكيد صفر تكلفة وعدم قبول التزام جديد. تقديم URL الفعلي والـJSON النهائي وخطة التحكم بالمفتاح وطريقة التراجع للمالك. لا استخدام GitHub Pages للمستودع الخاص تلقائيًا ولا جعل المستودع عامًا.
3. بعد موافقة منفصلة ومحددة فقط: إنشاء المفتاح في بيئة تشغيل آمنة يوافق عليها المالك؛ حفظ الخاص خارج المستودع والوثائق والسجلات؛ مراجعة العام فقط ثم نشر الملف المحدد. إعداد `Cache-Control: max-age=300, must-revalidate` مقترح لتقليل تأخر التدوير، وليس ضمانًا على سلوك كل مصدر.
4. بوابة حق البيانات المستقلة: توثيق نص شروط المصدر الذي يسمح تحديدًا باستعلام المستخدم وعرض السعر والتوفر في المقارنة التجارية، ونسب المصدر والاحتفاظ والتحديث، أو إذن واضح من المصدر. لا تواصل خارجي لطلبه دون موافقة المالك. إذا ظل الحق غير محسوم، يظل ألف معلقًا حتى لو نشرت الهوية.
5. بعد التصاريح المناسبة: اختبار اتصال محدود للمصدر، ثم بحث نصي AirPods 4 دون SKU يدوي، ثم UI → `/api/search` → المصدر. لا سلة ولا شراء؛ لا عنوان أو IP عميل. أي اشتراط إرسال IP العميل يوقف ذلك الإجراء ليُراجع؛ لا اختلاق IP.
6. حفظ دليل طلب/استجابة منقح وتوقيت وسعر وتوفر ومطابقة؛ الجودة المستقلة ثم مراجعة المالك. لا يصبح نجاح التجربة إذن نشر عام أو دمج.

## خيارات القرار

- الاستمرار في التحضير المحلي وفحص بدائل ذات إذن واضح: لا يحتاج نشرًا الآن (التوصية الحالية).
- الموافقة لاحقًا على نشر **ملف ومضيف ومفتاح عام محددين** بعد عرضها كاملة: موافقة تقنية محدودة، ليست إذنًا تجاريًا للبيانات.
- إبقاء ألف معلقًا إذا لم يتحقق الحق أو المصادقة ضمن صفر تكلفة؛ متابعة البدائل والأعمال المستقلة.
