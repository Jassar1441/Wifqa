# شركة وفقًا | سياسة إلزامية لمراجعة الجودة وموافقة المالك قبل الدمج أو النشر

**تاريخ تثبيت القرار:** 13 أكتوبر 2026
**صاحب القرار:** مالك مشروع «شركة وفقًا | WIFQA»
**الحالة:** قرار إدارة مشروع معتمد من المالك؛ هذا الملف **مسودة إدراج في GitHub** على فرع منفصل، ولم يُدمج بعد في `main`.

> **النص الحاكم من المالك حرفيًا:** «لا دمج في النسخة الرئيسية ولا نشر للمستخدمين إلا بعد اجتياز مراجعة الجودة والحصول على موافقتي.»

## نطاق سريان القرار
ينطبق على جميع المسؤولين/المساعدين/الأدوات، وعلى كل تغيير برمجي أو بصري أو نصي أو إعداد تشغيلي متعلق بوفقًا، بما في ذلك واجهات العملاء، التصميم، البنية، التكاملات، بيانات المتاجر، والتغييرات التي تؤثر في الأمان أو الخصوصية.

## بوابتان إلزاميتان قبل أي عملية دمج أو نشر

1. **بوابة مراجعة الجودة (QA):** تقرير مراجعة بتاريخ حديث يربط التغيير بمعايير قبول قابلة للتحقق، مع نتائج اختبارات مثبتة وروابط الأدلة وذكر النواقص والأخطاء والمخاطر وأي حدود في التغطية. لا تُعد شهادة منشئ التغيير وحدها مراجعة مستقلة كافية عندما تتوفر إمكانية فحص مستقل. إذا فشلت الجودة، يُعاد العمل ولا يتم الدمج أو النشر.
2. **بوابة موافقة المالك:** موافقة صريحة على التغيير المحدد بعد عرض ملخصه وتقرير الجودة وروابط المراجعة. السكوت أو الثقة العامة أو الموافقة على العمل المبدئي ليست إذنًا بالدمج أو النشر. لا يُفترض أن الموافقة على الدمج تشمل النشر أو العكس؛ يطلب الإذن الخاص بكل إجراء.

**الترتيب:** تجهيز تعديلات آمنة على فرع منفصل ← طلب مراجعة مسودة ← اختبارات ومراجعة جودة ← موافقة المالك على الدمج ← الدمج المصرح به. وإذا كان هناك نشر: مراجعة جاهزية نشر مستقلة ← موافقة المالك على النشر ← النشر المصرح به.

## ما يمكن فعله دون طلب موافقة متكررة
- قراءة وفحص الملفات والأخطاء، إعداد مواصفات وتقارير، توليد صور أولية، إنشاء تعديلات وفروع خاصة وطلبات مراجعة **مسودة**؛ دون دمج أو تغيير صلاحيات أو مشاركة عامة أو نشر أو إنفاق.
- توثيق المخاطر والتوصيات وحالة كل مهمة.
- تجربة محلية أو داخل بيئة منفصلة غير منشورة للمستخدمين، ضمن الصلاحيات الحالية ودون أثر عام.

## ما يُمنع دون إذن صريح
- الدمج في `main` أو أي فرع نشر/إنتاج، وتفعيل الدمج الآلي.
- إطلاق/نشر إصدار أو رابط عام أو تعديل بيئة مستخدمين حقيقية أو إرسال إعلان إطلاق.
- توسيع صلاحيات الأشخاص والتطبيقات أو جعل المستودع/المجلدات عامة أو مشاركة بيانات خاصة.
- شراء أدوات أو خدمات، أو إنشاء التزامات مالية باسم المشروع.

## قالب تقرير جاهزية القرار
- رقم المهمة/طلب السحب ورابط التغييرات:
- ما تغير، وما لم يتغير:
- مراجِع الجودة، التاريخ، رابط أدلة الاختبار:
- عدد الاختبارات والنتيجة مع بيان ما **لم** يُختبر:
- عيوب مانعة ونواقص ومخاطر متبقية:
- قرار مراجعة الجودة: مقبول للمراجعة / مرفوض / يحتاج استكمال.
- **الموافقة المطلوبة من المالك:** دمج محدد؟ نشر محدد؟ كلاهما بإذنين مستقلين؟
- **تاريخ وصيغة موافقة المالك الصريحة:** (تترك فارغة حتى يصدر الإذن).

## ملاحظة عن الإنفاذ التقني
هذا التوجيه ملزم في سير عمل المساعدين، لكنه **ليس بحد ذاته حماية تقنية** تمنع أي شخص لديه صلاحيات GitHub من الدمج. يُوصى لاحقًا، وبعد الموافقة اللازمة وتوفر وصول الإدارة، بإعداد GitHub branch protection أو repository rulesets لفرض الاختبارات والمراجعة على `main`، وقيود نشر للإنتاج. إلى أن يتم إثبات إعداد تلك الحماية، لا يجوز ادعاء أن GitHub يمنع الدمج تقنيًا.
